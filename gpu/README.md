# GPU 大规模重复实验（analysis model）

> 一句话：把「一个 CUDA 线程 = 一次完整仿真」这个天然的数据并行结构用起来，
> 在 RTX 3050 上 **1 秒多跑完 15000 次仿真**，给项目补上统计严谨性
> （均值 ± 95% 置信区间 + 配对显著性 + 参数扫描）—— 这是纯 Python 参考模型做不到的。

---

## 1. 为什么要有这个模块

项目 v1.1 有两个真实短板（`docs/01` 里如实记录过）：

1. **仿真是 wall-clock 驱动的**（`scheduler_tick_real_s=2ms` + `time.sleep`），
   一次 PEAK 工况要约 9 秒墙钟；
2. **单次结果带 3~5% 的运行噪声**，`simulation.repetitions` 这个开关在配置与文档里
   写了，但代码从未实现聚合。

于是报告里只能写「dynamic 跑了 25.86 个/秒」，**无法回答「这个差异是真的吗」**。

要做统计推断就必须重复很多次。按参考实现的成本估算：

```
15 个单元 × 2000 次 × 约9 s/次 约 75 小时
```

不可行。但注意：这几万次仿真彼此**完全独立**（每次是一个独立的随机实现），
是教科书级的 SPMD（单程序多数据）场景 —— 正好是 GPU 的主场。

## 2. 怎么做：一个线程 = 一个 replication

每个线程在自己的本地内存里完整跑一遍：

```
自带 RNG 播种 -> 生成两条到达流 -> 两级就绪队列 -> 调度决策 ->
服务/时间片抢占/弱网退避重传 -> 结算本次指标 -> 写回 out[rep]
```

关键设计：

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 消掉排序 | 每架无人机各维护「高优/低优」两条已排序到达流，主循环取两者最小值 | 避免一次 O(n log n) 排序（约 2000 个任务） |
| O(1) 队列 | `head/tail` + 每任务一个 `nxt[]` 链表指针 | 抢占/重传会反复入队，环形缓冲区容量难估 |
| 退避待办表 | `pend_idx/pend_due` 数组，到期才回到就绪队列 | 复刻 `simulator._retry_pending`：退避中的任务**不占并发槽位**，这是痛点①的解法 |
| 零同步 | 线程之间没有任何通信（不复用共享内存） | 单次仿真有几十万个操作，粒度足够大，没必要做块内规约 |
| 确定性 | 线程 `rep` 直接决定 RNG 种子 | 同 rep 同随机流，天然满足 CRN（共同随机数） |

**已实现的策略语义**（与 `src/uav_sim/scheduler/*.py` 一一对应）：

| mode | 策略 | 取任务规则 | 时间片 | 弱网处理 |
|---|---|---|---|---|
| 0 | FCFS | 跨两级队列取到达最早者 | 不抢占 | 指数退避 |
| 1 | RR | 同 FCFS | 固定 `rr_slice_ms` | 指数退避 |
| 2 | 静态优先级 | 高优绝对优先 | 不抢占 | 指数退避 |
| 3 | 动态权重 | 饥饿硬补偿通路 + 四因子权重比较 | 自适应（拥堵时收缩） | **链路感知：弱网走本地缓存** |
| 4 | MLFQ | aging 升权通路 + 分层 | level0 短 / level1 长（固定） | 指数退避 |

指数退避 = `retry_backoff_base_s × 2^min(retry-1, 3)`，与 `simulator.py` 一致。

> 曾经踩的坑：任务数触顶（`n == MAX_TASKS`）后如果还继续让 `next_arrival <= t`，
> 最早事件恒等于「到达」，仿真时钟 `t` 永不前进，内核空转到 guard 上限，
> 墙钟 2 分钟不返回。修复：触顶后把两条到达流置为 `1e30`。
> 这个 bug 说明 **「GPU 上不收敛」往往表现为「卡死」而不是报错**。

## 3. 怎么用

```powershell
# 一条命令：自动构建（缺失/过期才编）-> 运行 -> 统计 -> 出 CSV
& ".\.venv\Scripts\python.exe" run.py gpu --reps 3000
& ".\.venv\Scripts\python.exe" gpu\run_gpu.py --reps 3000 --compare   # 顺带和参考模型对照

# 参数扫描
& ".\.venv\Scripts\python.exe" gpu\run_gpu.py --sweep --reps 500

# 强制走纯 Python 回退（没有 N 卡 / 没有 CUDA 工具链时用）
& ".\.venv\Scripts\python.exe" gpu\run_gpu.py --backend python --reps 50

# 只构建内核
.\gpu\build.ps1              # 已是最新会跳过
.\gpu\build.ps1 -Rebuild     # 强制重建
```

### 三个后端（`--backend auto|cuda|python`）

| 后端 | 用什么 | 速度 | 什么时候用 |
|---|---|---|---|
| `cuda` | `replication_kernel.cu`（nvcc 编译） | **约 12000 次仿真/秒** | 有 N 卡 + CUDA 工具链（本机默认） |
| `python` | `des_model.py`（纯 Python + 多进程） | 约 40 次仿真/秒/核 | 没有 CUDA 环境时的**回退**，保证 `run.py gpu` 不会直接失败 |
| `auto` | 先试 CUDA，失败自动回退 Python | — | 默认 |

`des_model.py` 与 CUDA 内核是**同一套规则的两份实现**（同一个 xorshift64* RNG、
同一事件顺序），因此它既是回退路径，也是交叉验证基准（见第 6 节）。

> 关于 numba-cuda：本机装了 `numba-cuda` 且 `numba.cuda.is_available()` 为 True，
> 但**没有采用**它作为后端 —— 本模型需要大量可变状态（每线程十几个数组）与
> 嵌套辅助逻辑，numba 的 CUDA target 对此支持很差，硬写会得到第四份实现且
> 难以验证。nvcc 内核是主 GPU 路径，纯 Python 是回退，两条已经够用。

产物：`results/gpu/gpu_per_replication.csv`（逐次）、
`gpu_replication_summary.csv`（均值 ± 95% CI）、
`gpu_paired_dynamic_vs_priority.csv`（配对显著性）；
扫描模式出 `gpu_sweep_per_replication.csv` 与 `gpu_sweep_summary.csv`。

## 4. 实测性能（`--reps 3000`，五个策略）

RTX 3050 Laptop（4 GB 显存，16 个 SM）：

| 策略 | 3000 次耗时 | 吞吐 | 低优平均等待 | 低优饥饿率 | 业务完整率 |
|---|---|---|---|---|---|
| FCFS | 251 ms | 21.64 ± 0.13 | 6558 ± 112 ms | 8.31 ± 0.28 % | 69.26 ± 0.40 % |
| RR | 285 ms | 29.78 ± 0.03 | 803 ± 13 ms | 0.00 % | 95.32 ± 0.06 % |
| 静态优先级 | 133 ms | **8.84 ± 0.10** | 869 ± 9 ms | 0.55 % | **28.30 ± 0.31 %** |
| 动态权重 | 258 ms | 28.07 ± 0.04 | 3680 ± 23 ms | 0.48 % | 89.79 ± 0.15 % |
| MLFQ | 313 ms | 29.69 ± 0.02 | 1580 ± 10 ms | 0.00 % | 94.94 ± 0.03 % |

合计 **15000 次仿真 / 约 1.24 s ≈ 12097 次/秒**，置信区间已收窄到约 0.1%。
作为对比，Python 参考模型跑 1 次 PEAK 要约 9 秒。

配对比较（同 rep 同种子）里最硬的一条：

| 对比 | 指标 | 差值 ± 95% | 显著 |
|---|---|---|---|
| dynamic − priority | 吞吐量 | +19.24 ± 0.19 | 是 |
| dynamic − priority | 业务完整率 | +61.48 ± 0.62 % | 是 |
| dynamic − priority | 本地缓存次数（仅 dynamic 非零） | +92.94 ± 0.63 | 是 |
| dynamic − mlfq | 低优平均等待 | +2100 ± 25 ms | 是（dynamic 更差） |
| dynamic − mlfq | 高优平均等待 | +807 ± 105 ms | 是（dynamic 更差） |

> **如实记录**：在这个分析模型里，`mlfq` / `rr` 的吞吐与完整率都略优于 `dynamic`，
> 且时延更低。`dynamic` 唯一稳定的优势是**链路感知**（本地缓存生效、重传率更低）。
> 这与参考模型 `docs/01` §16.6 的负面结论一致（「链路感知并没有带来时延优势，
> 缓存把弱网任务推迟得更久，抬高了均值」）。报告里不应回避这一条。

## 5. 参数扫描：一个反直觉但重要的结论

```powershell
& ".\.venv\Scripts\python.exe" gpu\run_gpu.py --sweep --reps 500
```

默认扫描设计 = **饥饿阈值 `starvation_ms`（4 档）× 系数原型（6 组）= 24 组**
（为什么不是无脑全因子：见下面的结论）。

结果（`results/gpu/gpu_sweep_summary.csv`）：

```
  边际敏感性（该参数取不同值时，「业务完整率」的平均值）
    alpha     0.00->76.40   0.45->76.40   0.75->76.40
    beta      0.00->76.40   0.35->76.40   0.75->76.40
    gamma     0.00->76.40   0.15->76.40   0.60->76.40
    delta     0.00->76.40   0.25->76.40   0.75->76.40
    starve_ms 1000.00->93.94  3000.00->89.90  10000.00->75.61  30000.00->46.15
```

| 参数 | 对业务完整率的极差 | 结论 |
|---|---|---|
| `alpha` / `beta` / `gamma` / `delta` | **约 0.00 个百分点** | 在本工况下**几乎不影响结果** |
| `starvation_ms` | **47.78 个百分点** | 真正起作用的参数 |

**为什么？** 看 `promotions` 指标：PEAK 过载下，每次仿真约有 1578 次调度是走
「饥饿硬补偿通道」（绕过权重比较直接派发）的，而全程完成的任务约 1700 个。
也就是说**绝大多数低优任务是被确定性补偿通道救出来的，四因子权重根本没参与决策**。

**这意味着什么**（可直接写进报告的「改进方向」）：

1. 当前设计里「动态权重」这个卖点其实是**装饰性**的，真正解决饥饿的是那条硬通道；
2. 因此没有必要为 α/β/γ/δ 做精调 —— 它对结果不敏感，**鲁棒性好也是好事**；
3. 反过来，`starvation_ms` 是唯一需要认真标定的旋钮：调小（1000 ms）完整率 93.9%，
   调大（30000 ms）直接掉到 46.2%；
4. 要么把权重做成真正参与决策（例如降低硬通道优先级、只在权重接近时兜底），
   要么诚实地把算法描述为「确定性 aging 补偿 + 权重微调」。

> 一条方法论提醒：**参数扫描的价值不只是"找到最优"，更是"发现哪个旋钮根本没用"**。
> 如果只做 `run.py sensitivity` 那种 3 组点估计，这个结论是看不出来的。

## 6. 模型确认（model verification）

本内核**不是**逐位复刻，而是「同规则、不同实现」的分析模型。可信度靠两条证据：

### 6.1 与参考模型对照（`--compare`，自动生成）

| 策略 | 参考吞吐 | 分析模型吞吐 | 偏差 | 参考完整率 | 分析模型完整率 | 偏差 |
|---|---|---|---|---|---|---|
| FCFS | 15.14 | 21.64 | **+42.9 %** | 55.8 | 69.3 | +24.0 % |
| RR | 25.13 | 29.78 | +18.5 % | 92.4 | 95.3 | +3.2 % |
| 静态优先级 | 8.86 | 8.84 | **−0.2 %** | 32.6 | 28.3 | −13.1 % |
| MLFQ | 26.04 | 29.69 | +14.0 % | 95.9 | 94.9 | **−1.0 %** |
| 动态权重 | 25.86 | 28.07 | +8.6 % | 95.2 | 89.8 | −5.7 % |

**一致的（结论层）**：策略排序一致（`{rr, mlfq, dynamic}` 一档 >> `fcfs` > `priority`）；
最差策略 `priority` 的吞吐偏差只有 **−0.2%**；MLFQ 完整率偏差 **−1.0%**；
三个策略的完整率偏差都在 6% 以内。

**不一致的（如实声明）**：

* **FCFS 偏差最大（+42.9%）**：分析模型里运维任务近乎免费（0.01 s），
  削弱了参考模型中大任务造成的「护航效应（convoy effect）」；参考模型里
  低优任务虽然小但数量更多，队头大任务更容易把它们整体堵死。
* 分析模型未复刻参考模型的离线标定轨迹（`WorkloadTrace`）、
  任务分片（拒绝/切片）、单机配额，也不含天气扰动。
* 两者都用「等待 >15 s」做饥饿判定，但 `starvation_low_pct` 这个指标
  本身就会被「静态优先级几乎不产生低优完成样本」所扭曲（参考模型也这么认为）。

### 6.2 与纯 Python 实现交叉验证（同一套规则的两份实现）

`gpu/des_model.py`（纯 Python）与 CUDA 内核用的是同一个 RNG 与同一套事件顺序，
因此可以直接对比：

| 策略 | CUDA 内核（n=3000） | 纯 Python（n=20） | 差异 |
|---|---|---|---|
| FCFS | 21.64 | 21.45 | −0.9 % |
| RR | 29.78 | 29.92 | +0.5 % |
| 静态优先级 | 8.84 | 8.54 | −3.4 % |
| 动态权重 | 28.07 | 28.55 | +1.7 % |
| MLFQ | 29.69 | 29.68 | −0.0 % |

两条完全独立的实现给出几乎一致的结果 —— 这是「CUDA 移植没写错」的强证据
（比「数字看起来合理」可靠得多）。

## 7. 构建环境与踩过的坑

| 组件 | 路径 | 版本 |
|---|---|---|
| nvcc | `D:\CUDA Toolkit for hashcat\bin\nvcc.exe` | CUDA 13.3 |
| MSVC | `D:\Reverse tools\Visual Studio 2022\visual studio 2022` | 14.51（cl.exe 是 nvcc 的 host 编译器） |
| GPU | NVIDIA GeForce RTX 3050 Laptop, `sm_86`, 16 SMs | 见 `nvidia-smi` |

`build.ps1` 会自动拼 `PATH/INCLUDE/LIB`，并处理了三个隐蔽的坑：

1. **`-arch=$arch` 在 PowerShell 里不展开**，会原样传给 nvcc 报
   `Unsupported gpu architecture '$arch'` —— 必须先拼成字符串再传参。
2. **必须显式传 `-Xcompiler=/utf-8`**。源码注释是 UTF-8 中文，MSVC 默认按
   代码页 936 读，中文被误解码后可能产生 `0x5C`（反斜杠）尾字节，被当成
   **行继续符**吞掉下一行代码，报出一堆莫名其妙的「struct 没有这个成员」。
3. **`.ps1` 必须存成 UTF-8 with BOM**，否则 PowerShell 5.1 按 ANSI 读中文会直接语法报错。
   另外 nvcc 把 CUDA 头文件的代码页警告打到 stderr，配合
   `$ErrorActionPreference = 'Stop'` 会被当成致命错误 —— 需要临时放宽再自行判退出码。
