## 2. 时间模型（**必须严格遵守**）

1. **仿真时钟**：`Simulator.now()` = `(time.perf_counter() - t0) / cfg.time_scale`，单位「仿真秒」。
2. **一切时间戳都是仿真时间**，从 0.0 起算。禁止把 `time.time()` 写进 `Task.*_ts`。
3. **服务时长**：任务需要 `service_s` 仿真秒的服务；工作线程以 `service_s * time_scale` 真实秒的
   `time.sleep` 模拟 IO 传输（sleep 释放 GIL，因此不会退化成单线程）。
4. **指标口径**：等待时延、周转时间、饥饿判定全部换算为**毫秒**后记录（`* 1000`）。
5. `time_scale` 只影响跑多快，**不影响**任何指标的相对结论（可复现性来自固定 `WorkloadTrace`）。

## 3. 可复现性：`WorkloadTrace`（控制变量的核心机制）

「控制变量法」要求同一工况下所有策略面对**完全相同**的输入。因此**任务到达与链路质量都预先离线生成**，
一次 `(scenario, seed)` 只生成一份轨迹，5 个策略回放同一份轨迹。

```python
# scenarios.py
@dataclass(frozen=True)
class TraceEvent:
    t: float               # 仿真秒：任务到达时刻
    uav_id: int
    task_type: TaskType
    data_size_mb: float

@dataclass(frozen=True)
class ChurnEvent:
    t: float
    uav_id: int
    action: str            # "ONLINE" | "OFFLINE"

@dataclass
class WorkloadTrace:
    code: str                       # LIGHT/NORMAL/PEAK
    seed: int
    duration_s: float
    events: list[TraceEvent]        # 按 t 升序
    churn: list[ChurnEvent]         # 按 t 升序

def generate_trace(scenario: Scenario, seed: int, cfg: dict) -> WorkloadTrace: ...
```

**要求**：`generate_trace` 只用一个 `random.Random(seed)` 实例顺序消费，保证跨平台/跨 Python 版本
同 seed 同轨迹。相同 `(code, seed)` 两次调用结果必须逐元素相等（`tests/test_end_to_end.py` 会校验）。

```python
    {"code","offered_mbps","capacity_mbps","load_factor","avg_high_service_s",
     "avg_low_service_s","est_queue_depth","target_load_factor","verdict"}
    verdict ∈ {"ok","too_light","overloaded"}，偏差 >25% 记非 ok。
    供 `python run.py calibrate` 打印，用于说明"参数设计依据"（报告必需章节）。"""
```

**标定模型（三段式，写进报告）**

```
单任务服务时长(仿真秒)  = data_size_mb / (worker_bandwidth_mbps × link_factor)
    link_factor = weaknet_bandwidth_floor + (1 - weaknet_bandwidth_floor) × health/100

系统容量 capacity_mbps  = worker_threads × worker_bandwidth_mbps
提供负载 offered_mbps   = Σ(任务到达率 × 平均数据量)
系统负载 load_factor    = offered_mbps / capacity_mbps
```

> ⚠️ **教学案例原始参数存在量级不自洽**：把 100~2000 MB 的勘查任务按 0.5~1.5 s 间隔生成，
> 需求 >20 GB/s，任何服务器都不可能承载，会让三种工况全都退化为"完全拥塞"，无法对照。
> 因此本项目保留 PDF 的**数据量区间**与**运维任务间隔**（这两者符合现实），
> 把"勘查任务生成间隔"改为 `ops_interval × survey_gap_k`（勘查本就是"一趟作业一份大数据"，
> 比心跳稀疏得多），并通过 `calibrate()` 把三工况的 load_factor 标定到目标区间。
> 该处理与 rationale 必须写入 `docs/01-设计方案说明书.md` §工况标定。

```python
class MultiLevelQueue:
    """两级就绪队列（多级反馈队列的简化：HIGH / LOW 隔离排队）。

    线程安全：内部用 threading.Lock。lock_enabled=False 时故意不加锁，
    用于课堂反面演示「去掉锁会数据错乱」（对应实验一思考题 2）。
    """

    def __init__(self, capacity: int = 5000,
                 starvation_threshold_ms: float = 3000.0,
                 lock_enabled: bool = True) -> None: ...

    # ---- 入队 / 出队 ----
    def enqueue(self, task: Task, now: float) -> bool:
        """按 task.priority 放入对应队列，刷新 task.state=READY / enqueue_ts。
        返回 False 表示队列已满（任务被丢弃，调用方须置 DROPPED）。"""

    def dequeue_high(self, now: float) -> Task | None: ...
    def dequeue_low(self, now: float) -> Task | None: ...

    def dequeue(self, prefer_high: bool = True, now: float = 0.0) -> Task | None:
        """prefer_high=True 时高优先级队列非空则必取高优先级（严格优先）。"""

    def dequeue_starving(self, now: float, threshold_ms: float) -> Task | None:
        """饥饿补偿通道：从低优先级队列取出等待超阈值的任务（先进先出补偿）。"""

    def requeue(self, task: Task, now: float) -> None:
        """未执行完/被抢占/重传的任务放回原优先级队列队尾，requeue_count += 1。"""

    def drain(self) -> list[Task]: ...

    # ---- 状态视图 ----
    @property
    def high_depth(self) -> int: ...
    @property
    def low_depth(self) -> int: ...
    @property
    def total_depth(self) -> int: ...
    def depth_of(self, priority: TaskPriority) -> int: ...
    def congestion(self) -> float:
        """队列拥堵度 0.0~1.0 = total_depth / capacity。"""
    def starving_count(self, now: float) -> int: ...
    def oldest_wait_ms(self, priority: TaskPriority, now: float) -> float: ...
    def snapshot(self, now: float, running_count: int, blocked_count: int,
                 system_load: float, high_slice_ms: float, low_slice_ms: float,
                 high_weight: float, low_weight: float) -> QueueSnapshot: ...
```

### 4.4 `link_monitor.py` — core-engine

```python
class LinkState:
    """单条链路状态。health 由 delay/loss/rssi 综合评分。"""
    uav_id: int
    delay_ms: float
    loss_rate: float      # 0.0 ~ 1.0
    rssi_dbm: float
    def update(self, weaknet_level: str, rng: random.Random) -> None: ...
    def health_score(self) -> float:
        """0~100。建议公式（三者加权，越差分越低）：
        health = 100 × (0.40×delay_score + 0.40×(1-loss_rate) + 0.20×rssi_score)
        delay_score = clamp(1 - delay_ms/1000, 0, 1)
        rssi_score  = clamp((rssi_dbm + 100)/60, 0, 1)"""

class LinkMonitor:
    """全局链路监控。**确定性**：初始时按 (seed, uav_id) 为每台无人机预生成
    一条 0.5s 网格的健康度曲线，health_at() 线性插值 —— 因此轨迹可离线复现，
    且 5 个策略读到完全相同的链路序列（控制变量）。
    """

    def __init__(self, seed: int, weaknet_level: str, duration_s: float,
                 uav_ids: Iterable[int], cfg: dict) -> None: ...

    def register_uav(self, uav_id: int) -> None: ...
    def unregister_uav(self, uav_id: int) -> None: ...
    def health_at(self, uav_id: int, t: float) -> float: ...   # 纯函数式查询 0~100
    def get_health(self, uav_id: int) -> float: ...            # 当前时刻
    def get_all_health(self) -> dict[int, float]: ...
    def tick(self, now: float) -> None:
        """推进当前时刻并采集 LinkSample（落库用）。替代指导书里的阻塞 monitor_loop，

    def monitor_loop(self) -> None:
```

### 4.5 `resource_limiter.py` — core-engine

```python
class ResourceLimiter:
    """系统资源限流器：最大并发控制 + 单任务上限 + 单机配额 + 错峰。

    对应 OS 的「资源配额 + 并发限流」。注意：**它是系统级设施，对所有调度策略
    一视同仁**（否则无法做控制变量对照）。
    """

    def __init__(self, max_concurrent: int, max_task_memory_mb: float,
                 per_uav_quota: int, enable_chunking: bool = True) -> None: ...

    def try_admit(self, task: Task) -> str:
        """非阻塞准入判定，返回:
        "OK"              获得并发槽位，可以派发
        "THROTTLE"        并发已满 -> 调用方保留在队列中错峰（throttle_count += 1）
        "REJECT_LARGE"    单任务超过 max_task_memory_mb（reject_large_count += 1；
                          enable_chunking=True 时调用方应改走 split_task）
        "QUOTA"           该 uav 已占用 per_uav_quota 个槽位
        **状态变更只在返回 "OK" 时发生（必须原子）。**

    def acquire(self, task: Task, timeout_s: float = 0.0) -> bool:
        """保留指导书签名：阻塞式申请许可。timeout_s=0 表示等价 try_admit=="OK"。"""

    def release(self, task: Task) -> None:
        """工作线程任务结束后必须调用（含异常路径 finally）。"""

    def split_task(self, task: Task) -> list[Task]:
        """按 max_task_memory_mb 把大任务切成 N 个分片 Task（segment_total=N），
        每片继承 parent_task_id/priority/uav_id/submit_ts，data_size_mb 与 service_s 按比例拆。
        enable_chunking=False 时返回 []。"""

    def get_status(self) -> dict:
        """{"running":int,"available":int,"max_concurrent":int,"throttled":int,
            "rejected_large":int,"chunked":int,"released":int,
            "per_uav_running":{uav_id:int}}"""

    @property
    def running(self) -> int: ...
    def is_saturated(self) -> bool: ...
```

### 4.6 `simulator.py` — core-engine

```python
class UAVWorker(threading.Thread):
    """无人机节点 —— 映射为一个工作线程。"""
    def __init__(self, uav_id: int, sim: "Simulator", trace: WorkloadTrace) -> None: ...
    def run(self) -> None: ...
    # 线程主循环：按 trace 中属于本机的 TraceEvent.t 定时醒来 -> 创建 Task -> sim.submit_task()
    # 收到 sim.stop_event 置位后退出；上下线由 ChurnEvent 控制。

class Simulator:
    """仿真器主控 —— 相当于 OS 内核：管理无人机线程、就绪队列、工作线程池、
    链路监控、限流器与全局时钟。调度策略由外部注入（scheduler.step()）。
    """

    def __init__(self, scenario: Scenario, trace: WorkloadTrace, cfg: dict,
                 scheduler_name: str, seed: int) -> None: ...
    # 注入给调度器的公共组件（只读属性）
    queue: MultiLevelQueue
    link_monitor: LinkMonitor
    limiter: ResourceLimiter
    scenario: Scenario
    cfg: dict
    scheduler_name: str
    stop_event: threading.Event

    # ---- 时钟与队列 ----
    def now(self) -> float:
        """仿真时钟（秒）。"""
    def submit_task(self, task: Task) -> bool:
        """线程安全入队（生产者调用）。满了则丢弃并计数。"""
    def make_task(self, uav_id: int, task_type: TaskType, data_size_mb: float,
                  now: float) -> Task:
        """工厂：按当前链路健康度算 service_s 并构造 Task（不要自己 new Task，
        否则服务时长标定会不一致）。"""
    def compute_service_s(self, data_size_mb: float, uav_id: int, t: float) -> float:
        """data_size_mb / (worker_bandwidth_mbps × link_factor)，单位仿真秒。"""

    # ---- 执行 ----
    def dispatch(self, task: Task) -> bool:
        """把已通过 limiter 许可的任务交给工作线程池异步执行，返回是否受理。
        工作线程：sleep(service_s×time_scale) -> 弱网判定 -> 完成或重传 -> limiter.release()。
        任务完成后必须调用 scheduler.add_task_finished(task, exec_time)。"""
    def run(self, scheduler: "BaseScheduler", duration_s: float | None = None) -> dict:
        """主循环：启动 UAVWorker -> 循环调用 scheduler.step() 直到时长用尽 -> 收尾。
        返回 {"duration_s","tasks":list[Task],"queue_samples":list[QueueSnapshot],
              "link_samples":list[LinkSample],"context_switches":int,
              "overload_seconds":float,"limiter_status":dict,"dropped_in_queue":int,
              "stop_reason":str}"""
    def busy_workers(self) -> int: ...
    def system_load(self) -> float:
        """队列总任务需求 / 容量，供动态权重与过载判定使用。"""
    def is_overloaded(self) -> bool: ...
```

**弱网与重传规则（统一实现，所有策略共用，只有"是否感知链路"不同）**

```
任务在工作线程跑完 service_s 后：
    p_fail = (1 - health/100) × cfg.weaknet.retry_gain   , clamp 到 [0, 1]
    if random() < p_fail:
        task.retry_count += 1 ; state=BLOCKED
        → 若策略支持链路感知且 health < cache_health_threshold：
              state=CACHED，延迟 cache_retry_backoff_s 后重新入队（不占并发槽位）
          否则：
              延迟 retry_backoff_base_s × 2^(retry_count-1) 后原样入队（继续抢资源）
    else:
        task.state = DONE ; finish_ts = now
```

> 这就是痛点①「劣质链路长期抢占资源、优质链路资源闲置」的代码级复现机制：
> 静态策略没有链路感知，弱网任务反复重传持续占用槽位；动态策略会降权 + 缓存。

```python
class BaseScheduler:
    name: str = "base"
    label: str = "基类"
    #: 是否具备链路感知能力（决定弱网失败后走 CACHED 还是原样重传）
    link_aware: bool = False

    def __init__(self, sim, cfg: dict) -> None:
        self.sim = sim; self.cfg = cfg

        self.dispatch_count = 0
```

**五个策略的行为约定**

| name | 类 | 核心规则 | 预期表现（教学要点） |
|---|---|---|---|
| `fcfs` | `FCFSScheduler` | 单一 FIFO，不区分优先级 | 公平但无差别，核心任务被运维任务挤占，低优先级反而不会饥饿 → 说明"公平≠合理" |
| `rr` | `RRScheduler` | 固定时间片 `rr.time_slice_ms` 轮转，未完成放回队尾 | 响应均匀但上下文切换多、大任务抖动；时间片过小开销爆炸 |
| `priority` | `PriorityScheduler` | 严格优先级：高优先级队列非空必取高 | **低优先级任务饥饿**（可量化复现痛点②） |
| `mlfq` | `MLFQScheduler` | 多级反馈队列：新任务进高优先级队列，用完时间片降级到低队列；低队列定期升权（aging） | 缓解饥饿但参数敏感，弱网/过载下仍退化 |
| `dynamic` | `DynamicWeightScheduler` | 动态权重 + 饥饿硬补偿 + 自适应时间片 + 链路感知 + 过载收敛 | 高优先级时延↓、低优先级饥饿率↓、业务完整率↑（本方案） |

**`dynamic.py` 权重公式（冻结）**

```
Q   = queue.congestion()                          # 0~1 队列拥堵度
W   = min(1.0, task.wait_ms(now) / starvation_threshold_ms)   # 0~1 等待因子
L   = link_health / 100.0                         # 0~1 链路健康度
S   = min(1.0, max(0.0, sim.system_load()))       # 0~1 系统负载
base = base_high if task.priority is HIGH else base_low

W_raw = base × (w0 + α·Q + β·W + γ·L) × (1 - δ·S)

若 task.wait_ms(now) > starvation_threshold_ms:      # 饥饿硬补偿（防饥饿关键）
    boost = min(starve_boost_cap, 1 + starve_boost × W)
    W_raw *= boost

若 L×100 < cache_health_threshold:                   # 弱网降权
    W_raw *= 0.3
```

调度主循环 `step()`：
1. 先走饥饿补偿通道 `queue.dequeue_starving()`；若有候选且 `try_admit=="OK"` 则直接派发（保证低优先级有出路）。
2. 否则高、低队列各取队首候选，分别算权重，取权重高者。
3. `limiter.try_admit(task)`：
   - `"OK"` → 动态时间片 `slice = clamp(slice_base × (1 + slice_congestion_gain×Q), slice_min, slice_max)`，
     记录到 `self._high_slice_ms/_low_slice_ms` → `sim.dispatch(task)`
   - `"THROTTLE"` → 任务**留在原队列**（错峰），本轮不派发，`break`
   - `"REJECT_LARGE"` → `limiter.split_task(task)` 后把分片入队
   - `"QUOTA"` → 该任务放回并尝试另一优先级
4. 返回本轮派发数。

> 注意：`step()` 内部**不得**调用 `time.sleep`，休眠由 `Simulator.run()` 主循环负责。

# 附：v1.1 变更记录（开发期实测后的修订，**以此为准**）

> 契约 v1.0 是并行开发前冻结的**设计意图**；v1.1 是工程跑通后按实测数据修订的**事实版本**。
> 凡是本文档前面章节与本节冲突处，一律以本节为准。每一条修订都附"为什么改"的实测依据。

## 1. `MultiLevelQueue`：新增 `congestion_of(priority)` 与 `congestion_ref`

```python
def __init__(self, capacity=5000, starvation_threshold_ms=3000.0,
             lock_enabled=True, congestion_ref=32.0)
def congestion_of(self, priority) -> float   # 指定优先级队列的拥堵度 0~1
```

* **问题**：原设计 `congestion() = total_depth / capacity`，而 `capacity = 5000`、
  实际峰值堆积仅数百 —— `Q` 恒为 0.05~0.1，动态权重公式里的"对拥堵队列倾斜资源"
  **完全失效**（等价于 α = 0）。
* **修订**：新增 `congestion_ref`（默认 `4 × worker_threads = 32`，"积压超过 4 轮工作量即拥堵"），
  并按**优先级分别**计算 `congestion_of()` —— 拥堵是各队列各自的属性，
  高优先级队列堆 200 个而低优先级队列只有 3 个时不该共享同一个 Q。

## 2. 饥饿阈值拆成两个（**决策参数** vs **评价参数**）

| 配置项 | 值 | 用途 |
|---|---|---|
| `server.starvation_threshold_ms` | 1200 | 调度器 aging 触发点（dynamic 硬补偿 / MLFQ 升权） |
| `server.starvation_metric_threshold_ms` | 15000 | 计算"饥饿率"指标时的判定阈值 |

* **问题**：两者合一时，`dynamic` 在阈值处必然把低优任务补偿起来，
  于是低优任务"恰好等满阈值"，饥饿率被**设计性**钉在 ~55%，指标失去区分度（实测确认）。
* **修订**：语义分开 —— 前者是"该提权了"，后者是"业务上已经失联了"。

## 3. `BaseScheduler`：新增 `preempt_requeue` 与 `dispatch_admitted()`

```python
class BaseScheduler:
    preempt_requeue: str = "front"    # 'tail' = 轮转语义; 'front' = 保住排队位置
    def dispatch_admitted(self, task, now, slice_ms=None) -> bool   # 派发失败自动归还限流许可
    def push_front(self, task, now) -> None                         # 错峰放回队首并回滚等待记账
```

* `Simulator` 在时间片耗尽时按 `scheduler.preempt_requeue` 决定归位方式：
  `RR` / `MLFQ` 为 `"tail"`（这才是轮转），`dynamic` 为 `"front"`。
* **为什么需要 `"front"`**：勘查任务服务时长 ~11 仿真秒，若每次被抢占都排到
  400 个任务的队尾，峰值工况下永远轮不完 —— 实测高优先级任务完成率从 37% 掉到 24%。

## 4. `DynamicWeightScheduler`：Q 改为按优先级、时间片按类别差异化、预抢占阈值

```
Q = queue.congestion_of(task.priority)          # 不再是全局 congestity
slice_HIGH = 拥堵度 < 0.15 ? 不抢占 : clamp(1500 × (1 − 0.6·Q), 400, 3000)
slice_LOW  = clamp(200 × (1 − 0.6·Q), 100, 400)
```

* **轻载不切分高优先级任务**：LIGHT 工况下切片只会增加"派发-抢占-归位"，
  把高优平均等待从 442 ms 拉到 2620 ms（实测）。
* **按类别差异化时间片**：HIGH 用长时间片（大任务少轮次跑完）、LOW 用短时间片
  （任务本身只有几十毫秒，短片即可，且降低队头阻塞）。

## 5. 新增配置：`weaknet_downweight`、`mlfq:` 段

* `dynamic_weight.weaknet_downweight = 0.60`（原硬编码 0.3）。探针实测 0.3/0.6/1.0
  对吞吐影响 <1%，取 0.6 作为"弱网降权但不至于把任务永久压死"的折中。
* `mlfq.slice_level0_ms=300 / slice_level1_ms=800 / aging_ms=1500` 显式进 config
  （原先全走代码默认值，违反"参数全走 config.yaml"的开发规范）。

## 6. 弱网重传参数修订

| 参数 | v1.0 | v1.1 | 依据 |
|---|---|---|---|
| `weaknet.retry_gain` | 1.20 | **0.50** | 1.2 时 PEAK 的 `p_fail≈0.58`，需求被放大 **2.4 倍**，三工况一起退化为"重传风暴"，饥饿率饱和、策略差异被掩盖 |
| `weaknet.retry_backoff_base_s` | 0.5 | **0.20** | 退避上限从 8 s 降到 1.6 s；退避太久会让任务"消失"于队列之外，既不真实也稀释统计 |

## 9. 指标口径澄清（报告必写）

`completion_rate`（业务完整率）按**任务条数**统计，而 PEAK 工况中低优先级任务占条数
约 97% —— 因此该指标会被低优先级任务"抬高"。业务真正关心的是**核心勘查数据的完成率**，
必须另外按优先级/按数据量统计（SQL 见 `docs/05-数据库设计说明.md`）：

```sql
SELECT priority, COUNT(*) total, SUM(state='DONE') done,
       ROUND(SUM(state='DONE')/COUNT(*)*100,1) done_pct,
       ROUND(SUM(CASE WHEN state='DONE' THEN data_size_mb ELSE 0 END)
             / SUM(data_size_mb)*100,1) bytes_pct
FROM task_record WHERE exp_id = ? GROUP BY priority;
```
