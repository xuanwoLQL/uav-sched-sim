## 3. 答辩口径（每行一句话，背这一列即可）

> 用法：被问"你这个功能对应什么原理"时，先给**现象**，再给**原理**，最后给**证据**（指标名或表名），不要只讲代码。

1. **拥堵**：30 架同时上传 → 就是多个生产者线程抢同一个就绪队列 → 我们做了双队列隔离 + 队列容量上限，证据是 `peak_queue_depth` 和 `charts/06` 的堆积曲线。
2. **任务**：一次上传就是 OS 里的一个 CPU-IO 混合任务（TCB）→ 我们用 `Task` 的七态状态机 + 带宽标定的 `service_s` 来刻画，证据是 `task_record` 每行的 `submit_ts→finish_ts`。
3. **上下线**：无人机返航就是线程销毁 → 生产者线程按 churn 事件流停/启，证据是 PEAK 的 156 条 churn 事件与下线期间不产生任务。
4. **饥饿**：运维任务传不上去 = 低优先级进程长期拿不到 CPU → 我们做了饥饿检测 + 硬补偿通道，证据是 `starvation_rate_low`（静态优先级 65.7% vs 动态 0%）。
5. **护航**：2 GB 点云堵住 0.6 MB 告警 = 非抢占调度的队头阻塞 → 我们用时间片抢占 + 自适应时间片，证据是 `context_switch` 与 `p95_wait_high_ms`。
6. **过载**：峰值把服务器打满 = 并发许可耗尽 → 我们用非阻塞 `try_admit` 做错峰而不是阻塞等待，证据是 `running_count` 恒 ≤ 8、`throttle_count` 上千次。
7. **单机霸占**：一架占满通道 = 缺单进程配额 → `per_uav_quota=2`，证据是 `per_uav_running` 与 `quota_blocked`。
8. **大任务**：1.2 GB 超上限 = 大段内存请求要分页 → 我们"拒绝计数 + 切片重传"，证据是 `reject_large_count`、`chunk_count` 与 `demo-limiter` 的 3×400 MB。
9. **弱网**：时延丢包 = I/O 设备阻塞率 → 我们把它折成 0~100 健康度，既改服务时长也改失败概率，证据是 `link_sample.health` 与 `retry_rate`。
10. **失衡**：弱网任务反复重传抢资源 = 慢设备拖住 CPU → 我们权重降 40%（×0.60）+ `CACHED` 缓存退避，证据是 `task_record.cached` 计数（PEAK-dynamic 406 条，其他策略 0）。
11. **静态优先级**：现有系统优先级写死 → 严格优先必然饿死低优先级，这是**我们故意保留的对照组**，证据是它 `starvation_rate_low` 最高、`completion_rate` 最低。
12. **FCFS**：谁先到谁先传 → 公平但无差别、护航效应明显，证据是它高优先级时延与 P95 最差。
13. **RR**：固定时间片轮流 → 响应均匀但切换开销大，证据是 `context_switch` 1518 次、`avg_requeue` 上升。
14. **MLFQ**：给低优先级一条制度化上升通道 = aging 老化提权 → 饥饿确实降到 0，但参数写死、切换最多（1991 次）。
15. **动态权重**：参数固化跟不上工况 → 四因子权重让 `base` 只占约 1/4，其余由队列/等待/链路/负载实时决定，证据是 `queue_sample` 里权重随时间变化而静态策略恒为 1.0。
16. **资源倾斜**：拥堵队列该多拿 CPU → 拥堵度按优先级分别算（`congestion_of`，基准 32 = 4×线程数），证据是权重与队列深度同向；用 5000 归一化会退化成没有拥堵感知。
17. **削峰**：过载还全速接单 → `(1−δS)` 压缩权重 + 入口限流，证据是 `overload_seconds` 与 `system_load` 曲线。
18. **可复盘**：内核有 ftrace/perf，我们有 `exp_metric` + `task_record` + `queue_sample` + `link_sample`，全部挂 `exp_id` 外键，任何一个平均值都能下钻。
19. **可复现**：控制变量法要求输入固定 → 任务与链路都离线预生成，5 个策略只做回放，`tests/test_end_to_end.py` 断言同 seed 同轨迹。
20. **标定**：工况不能拍脑袋 → 用 λ/μ 五式反解 `survey_gap_k`，让负载率命中 0.22/0.85/1.38，证据是 `run.py calibrate` 的标定表与 `scenario_def` 表。

## 4. 三条容易被追问的"边界说明"（提前准备好）

| 追问 | 诚实回答 |
|---|---|
| "你的动态策略是不是全面最优？" | 不是。它换来的是**低优先级公平性 + 更少上下文切换**；在 PEAK 工况下高优先级任务的**逐条完成率**并不比静态优先级高（见 01 §16.5 的口径讨论），因为饥饿硬通道与弱网降权都在替低优先级/劣质链路"让路"。这是明确的设计取舍，也是后续优化点。 |
| "`completion_rate` 95% 是不是说明业务没丢？" | 要分优先级看。PEAK 工况下低优先级任务占**条数**的 97.8%，把整体完成率抬高了；单看高优先级勘查任务，各组只有 16%~50%。所以报告中同时给出**按优先级的完成率**与**按字节的业务完整率**两种口径。 |
