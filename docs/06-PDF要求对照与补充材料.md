## 二、8 道开放性问题参考答案

> 答案全部基于本工程的**真实实测数据**（seed 20261031，PEAK 负载率 1.57）。数据可在
> `results/summary.csv` 与 MySQL `v_exp_summary` 中复现。

### 基础题

**问题 1：固定时间片轮转导致了哪些问题？根本原因？**

实测（PEAK 工况）：RR 的上下文切换 **≈1500 次**，比静态优先级（≈300 次）高 5 倍；平均等待时延 25889 ms。
根本原因：① **时间片与任务粒度不匹配**——勘查任务需 ~11 仿真秒服务，而时间片 500 ms，一个任务要被切 20 多次，
每次重新入队都排到队尾，在 60+ 深度的队列里"排队时间 ≫ 有效服务时间"；
② 切换本身有开销（保存/恢复 TCB、线程池调度），系统把 CPU 花在"换人"上而不是"干活"上。
`run.py sensitivity` 的 B 组给了量化证据：时间片 120→500→3000 ms，完整率 96.1%→92.3%→75.3%（片太大退化成 FCFS），
低优饥饿率 0%→0.2%→27.0%（片太大导致低优先级长期轮不到）。

**问题 2：瞬时并发冲击下，过载是哪些资源被耗尽？**

三类，且本工程可分别观测：
① **并发槽位**（= 工作线程数 8）：`ResourceLimiter.try_admit()` 返回 `THROTTLE`，PEAK 下累计触发 **>6000 次**；
② **队列容量**（5000）：`queue.dropped_full` 计数，PERK 峰值堆积最高数百，尚未触顶（说明瓶颈先在槽位）；
③ **单任务内存/数据量配额**（2048 MB）：`rejected_large` 计数为 0（工况最大 2000 MB），
但 `run.py demo-limiter` 用 500 MB 上限演示了 1200 MB 任务被拒 + 切 3 片。
另外 `system_load = 积压服务秒 / (8×2s)` 在 PEAK 达到 **>30**，远大于 1，即积压按满负荷也要 60 s 以上才能排空。

**问题 3：画出四种策略任务完成时间对比图，并解释动态权重为何降低核心业务等待时延。**

图见 `charts/02-平均等待时延对比.png`（高/低优先级分图）。PEAK 实测高优先级平均等待：
FCFS 32124 ms、静态优先级 21252 ms、MLFQ 25990 ms、**动态权重 29907 ms**。
诚实结论：动态权重**没有**在这项上最优——静态优先级因为"完全不给低优先级"所以高优最快。
动态权重的价值在于**同时**把低优先级饥饿率从 66.5% 压到 0%、完整率从 56.0% 提到 95.2%。
真正让动态权重占优的是"综合指标"而非单一高优时延；这一点在报告 §16.5 已如实写明，答辩时应主动说明。

**问题 4：静态优先级造成任务饥饿，技术漏洞体现在哪？**

三处：① 调度判据只有 `priority` 一个静态字段，**没有任何"等了多久"的输入**（对照 `dynamic._weight()` 里的 W 因子）；
② 没有 aging 机制，高优先级队列永不为空时低优先级**永远**轮不到（实测低优饥饿率 66.2%）；
③ 没有链路感知，弱网任务反复重传仍按原优先级抢槽位，进一步挤压低优先级。
代码级证据：`priority.py::step()` 只要 `dequeue_high()` 非空就绝不取低队列。

### 进阶题

**问题 5：硬件扩容 vs OS 调度优化，四维度评估。**

| 维度 | 硬件扩容 | OS 调度优化（本方案） |
|---|---|---|
| 成本 | 持续采购 + 带宽租赁 | 一次性开发，无经常性支出 |
| 周期 | 短（采购即用） | 中（2–3 周开发调试） |
| 技术风险 | 低 | 中（并发 bug、参数整定） |
| 长期可维护性 | 差（规模再涨还要加） | 好（改 `config.yaml` 即可调参） |

选择优化方案。量化依据：本工程在**同一硬件**（8 线程 × 150 MB/s）上，把 PEAK 完整率从 56.0% 提到 95.2%、
吞吐从 15.2 提到 25.9 个/s —— 相当于**不花钱获得 1.7–2.9 倍等效容量**。硬件要达到同样效果需扩容约 2 倍。

**问题 6：设计权重系数的自适应调整策略。**

本工程的做法（已实现，`config.yaml::dynamic_weight`）：
`W = base × (w0 + α·Q + β·W_wait + γ·L) × (1 − δ·S)`，其中 S 是归一化系统负载。
自适应体现在三处：① **Q 按优先级分别计算**（`congestion_of`），哪个队列堵就给谁加权；
② **时间片随拥堵收缩** `slice = base×(1−0.6Q)`，过载时切得更细以压低队尾延迟；
③ **饥饿硬补偿** `W *= min(6, 1+1.8·W_wait)`，保证低优先级等待有上界。
不同工况表现（预测→实测）：轻载 S≈0，退化为"带 aging 的优先级"；峰值 S→1，整体降权 25% 并靠 Q 做削峰。

### 拓展题

**问题 7：扩展到多地面站的跨服务器负载均衡架构。**

需要新增：① **分布式队列**（Redis/Kafka 分片队列，替代进程内 `MultiLevelQueue`）；
② **跨节点一致的负载视图**（本工程 `system_load()` 是进程内计算，分布式需心跳聚合）；
③ **分布式限流**（`ResourceLimiter` 的槽位要变成 Redis 令牌桶，否则 N 台各限 8 并发 = 8N）；
④ **一致性哈希路由**（同一架无人机的任务尽量落同一地面站，避免任务乱序）；
⑤ **脑裂与网络分区**（分区时两侧各自调度，恢复后要能对账）。
原理异同：相同点是"就绪队列 + 优先级 + 限流"这套模型不变；不同点是**排队时间从 μs 级变成 ms 级**，
`starvation_threshold_ms` 这类参数要按网络 RTT 重新整定。

**问题 8：基于 OS I/O 管理原理的弱网自适应调度策略。**

本工程已实现三件事：① **健康度评分**（`LinkState.health_score()`：时延 40% + 丢包率 40% + 信号 20%）；
② **弱网降权**（健康度 < 40 时权重 ×0.6）；③ **本地缓存 CACHED**（`_on_upload_failed` 中
`link_aware=True` 且健康度 < 阈值时，任务进入 CACHED 状态、退避 2 s、**不占并发槽位**）。
效果：PEAK 下动态权重的弱网重传率 39.5%，静态策略则表现为"劣质链路反复抢槽位"。
**诚实记录**：`run.py sensitivity` 的 C 组（弱网加剧）显示，本方案的 CACHED 退避会把弱网任务推迟过久，
高优时延反而最高（32959 ms vs MLFQ 28089 ms）——这是"缓存退避太粗"的已知缺陷，改进方向：
缓存任务只降权不退避，或为弱网任务单开一条低带宽独占通道。
