**关键实现要点（做实验时必须能指出来）**

1. **时间模型**：`Simulator.now() = (time.perf_counter() - t0) / time_scale`，所有 `*_ts` 都是仿真秒；`time.sleep(service_s × time_scale)` 模拟 IO，sleep 释放 GIL 所以 8 个工作线程是**真并发**。
2. **确定性**：任务到达与链路质量都**离线预生成**（`generate_trace(seed)`、`LinkMonitor._build_series()`），运行时不再掷骰子，这是后面 3.2~3.4 能成立的前提。
3. **线程安全**：`Simulator.submit_task()` 用 `self._lock`（RLock）保护 `_tasks` / `_by_id`；`MultiLevelQueue` 用 `threading.Lock` 保护双 deque。锁获取顺序固定为 `Simulator._lock → queue._lock / limiter._lock`，禁止反向。

**必须理解的三个实现细节**

1. **等待时延在出队时"结账"**：`_pop_with_accounting()` 把 `now - enqueue_ts` 累加进 `wait_ms_total`。若在入队时结算，重传/放回会重复计时。
2. **错峰要"回滚账"**：`push_front()` 会把出队时加上的那段等待**扣回**，否则"取出→判定限流→放回"每轮都白刷一次等待，几秒内就能把等待时延刷成天文数字。
3. **FCFS 的"全局 FIFO"是跨两个物理队列做的**：`base._take_global_fifo()` 先比较两侧队首的 `_arrival_key()`（入队时刻 → 提交时刻 → task_id），再只取走被选中的那一个；不能用"高队列优先"冒充 FCFS，否则它就不是基线了。

| 1 | 队列堆积量、等待时长、系统负载、链路质量四维权重 | `scheduler/dynamic.py : DynamicWeightScheduler._weight()`（Q/W/L/S 四因子） |
| 2 | 时间片动态调整，拥堵队列倾斜、空闲队列回收 | `dynamic._slice_for(priority, Q)`：**按任务类别**分别计算（HIGH 400~3000 ms、LOW 100~400 ms），并随队列拥堵度收缩；拥堵度低于 0.15 时不切分 HIGH |
| 3 | 饥饿补偿：长期等待的低优先级自动提权 | `dynamic.step()` 第 ① 步硬通道 + `_weight()` 中 `1 + starve_boost×W`（上限 `starve_boost_cap`） |
| 4 | 适配弱网：随通信质量、设备负载实时调整 | `_weight()` 的 γ·L 项 + 健康度 < `cache_health_threshold` 时 ×0.60（`weaknet_downweight`）；`simulator._on_upload_failed()` 的 `CACHED` 分支 |

**公式（与代码逐字对应）**

```text
Q = queue.congestion_of(task.priority)            # 该优先级队列的拥堵度 ∈ [0,1]
W = min(1, task.wait_ms(now) / starvation_threshold_ms)
L = link_health(task.uav_id) / 100
S = clamp(sim.system_load(), 0, 1)
base = base_high(1.00) 或 base_low(0.35)

W_raw = base × (w0 + α·Q + β·W + γ·L) × (1 − δ·S)
若 wait > starvation_threshold_ms: W_raw ×= min(starve_boost_cap, 1 + starve_boost·W)
若 L×100 < cache_health_threshold: W_raw ×= 0.3
```

系数取值：`w0=0.50, α=0.45, β=0.35, γ=0.15, δ=0.25, base_high=1.00, base_low=0.35, starve_boost=1.80, starve_boost_cap=6.0`（全部在 `config.yaml` 的 `dynamic_weight` 段，可直接改）。

**必须理解的三个设计决策**

1. **为什么 `try_admit` 非阻塞**：调度决策发生在调度线程上，一旦 `acquire()` 阻塞，就没人派发其它任务 → 8 个槽位空着也无人使用 → 死锁。所以 `try_admit` 返回 `THROTTLE` 时任务**留在队列**错峰（对应 OS：资源不足时进程仍在就绪队列等待下一次调度）。
2. **为什么拥堵度要按优先级分别算**：`congestion()` 用总深度归一化，会让"高队列堆 200 个、低队列 3 个"共享同一个 Q，向拥堵队列倾斜就落空了。`congestion_of(priority)` 才是 Q 的正确口径。
3. **为什么限流器对所有策略一视同仁**：限流是**系统级**资源管控，不属于调度策略。若只给 dynamic 配限流，实验就变成"策略差异 + 容量差异"的混合，控制变量失效。
